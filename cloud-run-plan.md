# Weekly KSeF → Google Tasks on Cloud Run — Execution Plan

## Goal and scope

Deploy a private Go HTTP Cloud Run function from GitHub. Cloud Scheduler invokes it weekly. The function fetches received KSeF invoices and creates one task per eligible invoice in a new Google Tasks list owned by the designated Workspace user, dated one calendar day before the payment deadline. Create tasks ahead of time during the weekly run; do not wait for each task date to arrive.

Keep the existing local CLI and `export-ics` working; the cloud workflow must not create calendar events or require a Calendar API scope. No payment ledger, correction reconciliation, installment inference, calendar migration, or cloud archive of invoice XML in this plan. If creating a task at a specific time or on the day itself is required, agree on a different scheduling design before implementing: a weekly scan cannot guarantee that timing, and the [Tasks API](https://developers.google.com/workspace/tasks/reference/rest/v1/tasks) stores only a date, not a due time.

## Current state and evidence

- `cmd/pylon/main.go` runs a local command, authenticates via `internal/ksef/client.go`, and calls `internal/sync.Run`. Sync uses permanent-storage dates, independent subject checkpoints, pagination and a KSeF completeness watermark. It currently depends directly on `*storage.Store`.
- `internal/storage/storage.go` relies on local Linux `flock`, rename, and `fsync`. Cloud Run instance storage is not durable across revisions or instances; do not deploy this filesystem as checkpoint storage or mount an object store to mimic its guarantees.
- `internal/calendar/ics.go` implements the reusable FA(2)/FA(3) rule: exactly one explicit valid payment date, no descriptive or multiple terms. It neither checks payment status nor reconciles corrections. The cloud design reuses the extraction rule, not ICS generation.
- `go.mod` requires Go 1.27.2 and `AGENTS.md` requires Go 1.27. `.github/workflows/ci.yml` checks formatting, vet, tests, race tests, and CLI build. Local baseline `go test ./...` passed with Go 1.27.4. No LSP server was configured; navigation fell back to repository search. No external credentials, deployments, or integrations were exercised.

## Confirmed decisions and rollout defaults

1. **Schedule:** Create tasks during the weekly scan, with a due date of **payment deadline minus one calendar day**. Proposed schedule: Mondays at 08:00, `Europe/Warsaw`. Weekly discovery can miss the intended date. Confirmed fallback: if the intended task date has passed but the payment deadline is today or later, make the task due today; if the payment deadline has passed, skip the invoice. Compare dates in `Europe/Warsaw`.
2. **Invoice scope:** Received invoices only, one taxpayer. Interpret “current month” as the **initial lookback**: start at midnight on the first day of the first run's month in `Europe/Warsaw`, using KSeF permanent-storage time. Persist that starting point before discovery so retries crossing month-end do not change it. Then resume from the saved cursor even across months, so a run on the first Monday of a new month does not skip invoices from the preceding week. This is not an issue-date or payment-deadline filter.
3. **Tasks and payment status:** During setup, create a new list (proposed name: `KSeF Invoice Payments`) as the designated Workspace user and configure its list ID. Use a separate list for TEST. Use the user's one-time consent and offline OAuth with the Tasks write scope, not the Cloud Run service account as task owner. Check Workspace admin policy and refresh-token suitability for unattended use. A completed task is the invoice's paid indicator; an open task is not paid, and a missing or deleted task is not evidence of payment. The app does not verify bank payments. Do not send credentials in chat or commit them.
4. **Deployment ownership:** The target is [rkorkosz/pylon](https://github.com/rkorkosz/pylon). Deliver code, deployment configuration, and instructions to the repo. The owner will connect GitHub to Google Cloud after the code is there. Project, region, and credentials can be selected during setup and do not block local implementation. Use separate TEST service/state/list before production.

## Phase 2 — Reuse KSeF discovery with durable cloud staging

- [x] Extract the payment parser from `internal/calendar/ics.go` into a proposed `internal/invoice` package and reuse it from ICS and cloud code. Share existing identifier/document/hash validation rather than weakening it on the cloud path. Keep legacy CLI behavior and tests intact.
- [x] In `internal/sync/sync.go`, introduce a narrow context-aware persistence seam around invoice handling and checkpoints, with an adapter for the existing `internal/storage.Store`. Preserve paging, date windows, stable bounds, watermark behavior, and checkpoint semantics. Capture a fixed end per invocation; treat a lagging watermark as incomplete even when some coverage committed.
- [x] Add a proposed Firestore adapter (e.g. `internal/cloudstate`) with a received-invoice cursor and deterministic task-intent keys scoped to deployment/destination, KSeF environment, taxpayer, and invoice identity. For each invoice, durably stage a minimal task intent or policy-skip record before advancing the window cursor; replay must not overwrite a task already created. Verify or download and parse invoice XML in memory; do not persist raw XML. Store only the fields needed for dispatch and recovery; never include amounts, parties, or bank details in tasks or logs. Persist the one-time Warsaw month-start bootstrap before discovery and resume from the last committed cursor thereafter; never reset it based on the current month.
- [x] Serialize a namespace's runs with a Firestore lease and ownership checks on state writes, sized to cover the bounded work deadline. Use per-intent transactional claims before task dispatch as a second guard against overlap, including across revisions. Cloud Run concurrency/instance limits are defense in depth, not the durable lock. Keep TEST and production state and lists isolated.

**Acceptance:** Existing CLI tests pass. New fake/emulator tests prove a crash before checkpointing replays without duplicating intents, checkpoint failures do not skip records, overlap cannot advance stale state, cloud discovery requests only received invoices, retries and normal runs span month boundaries without gaps, and missing/lagging watermarks do not falsely advance coverage. Verify with `go test ./...`, including a documented Firestore emulator target or procedure for transaction tests.

## Phase 3 — Dispatch Google Tasks safely from the function

- [x] Add proposed `internal/tasks`, `internal/runner`, and a root `function.go` registering an HTTP handler (proposed entry point `SyncInvoices`). Use request context and a bounded run deadline, accept POST only, validate non-secret configuration (environment, taxpayer, task list ID, Firestore settings) with received-only discovery and Warsaw date rules, and read secrets via the runtime identity. No credentials or invoice data in HTTP bodies/logs.
- [x] Compute deadline minus one **calendar** day without converting midnight through a different timezone. Apply the agreed late-invoice policy at dispatch so a retried intent cannot retain an unintended past task date. Use a short title with the invoice reference and put the original payment deadline and an opaque reconciliation marker in notes. Treat Workspace task status `completed` as paid when inspecting an existing task. Do not mirror a separate paid flag or infer payment from deletion. Do not overwrite, reopen, or recreate a known task; a locally recorded task ID prevents reinsertion even if that task was later deleted.
- [x] Drain pending intents independently of discovery and attempt delivery of already staged work even on a partial KSeF result, within the deadline. Persist a dispatching state before sending `tasks.insert`, then record Google's task ID on success. Do not blindly retry an insert after an ambiguous timeout, server failure, or crash after sending it. Reconcile by marker using paginated list results, including completed/hidden tasks when available. If there is no unique match, keep the intent unresolved, alert, and require operator review before resetting it; a missing list result is not proof that no task was created. Document the trade-off: avoid a likely duplicate rather than promising exactly-once across two APIs. Known safe transient failures can be retried with bounded backoff; stale claims go through reconciliation, not straight back to insert.
- [x] Return success only for complete discovery and dispatch (including no new work). Signal transient/incomplete results for bounded Scheduler retry; flag permanent configuration/authorization failures and unresolved inserts prominently for operator follow-up. Return no invoice identifiers or upstream error details to callers. Emit structured counts for discoveries, skips, tasks created, deferred windows and unresolved intents.

**Acceptance:** Tests cover calendar-day arithmetic across month/year/leap day and Warsaw DST, unsupported terms, agreed late-invoice rules, repeated invocations, OAuth failure, timeout/cancellation, and crashes on both sides of `tasks.insert`. Simulate an accepted insert followed by a lost response and verify the next invocation recovers the task ID without a second insert. Simulate no unique match and verify alertable unresolved state. In an authorized new Workspace test list, confirm the displayed task date is correct. Complete a task and rerun: the invoice is treated as paid and the task stays completed without a duplicate. Verify deletion is not treated as payment and does not silently recreate a task.
